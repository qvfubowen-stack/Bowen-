## 3. 多少产品类型未知

**466 个（全部，100%）。**

### 3.1 为什么是全部

**原始 Excel 里根本没有产品类型这一列。**

规划 V1 第 10.1 节明确规定：`product_type` **「必须人工确认」**。
所以程序把 466 个产品的 `product_type` 全部写为 `review_required`，**一个都没有猜**。

### 3.2 为什么不能猜

我用关键词做了统计（**只统计、不采用**）：

| 从原文能看出什么 | 产品数 | 占比 |
|---|---|---|
| **完全没有任何类型线索** | **420** | **90.1%** |
| 提到 `assembly`（总成） | 20 | 4.3% |
| 提到 `insert`（插入式） | 13 | 2.8% |
| 提到 `electronic`（电子式） | 11 | 2.4% |
| 提到 `housing`（壳体） | 4 | 0.9% |
| 提到 `water pump`（水泵） | 4 | 0.9% |
| 提到 `sensor` / `switch` | 2 | 0.4% |

（部分产品命中多个关键词，所以合计大于 466。）

**这 90% 的空白意味着**：如果程序强行把 466 个产品分成
`Thermostat` / `Thermostat Assembly` / `Thermostat Insert` 三类，
那就是**在编造数据**——其中大约 90% 的分类会是错的。

**需求已经明确禁止这么做**，我也确实没有做。审核表里的 `Confirmed Product Type` 列
**100% 是空的**，验收测试会强制检查这一点。

### 3.3 我只提供了"参考提示"，不是分类

审核表里有一列叫 **`Type Hint (参考，非确认)`**，内容是：

- 如果原文没线索 → `参考：原文无类型证据，请人工判断`
- 如果原文提到 → `参考：原文提到 Thermostat Assembly（仍需人工确认）`

**这一列只是帮你快速定位，不是结论，也不会写进数据库。**
数据库里的 `product_type` 依然是 `review_required`，等你填。

## 4. 多少涉及跨工作表 OE 差异

| 指标 | 数量 |
|---|---|
| 存在跨表 OE 覆盖差异的 Bowen 编号 | **286** 个 |
| 涉及的产品数 | **157** 个 |
| **第一批 72 个候选中的编号** | **58** 个 |
| 全部差异行数（一行 = 一个"编号 × OE 号"） | **1,843 行** |
| **其中属于第一批候选、需要优先审核的行数** | **881 行** |

### 4.1 先说清楚：这不一定是错误

需求明确要求「不要认为一定是错误」。**我同意，而且程序也没有这么认为。**

同一个 Bowen No. 在不同工作表里 OE 不一样，**可能是完全正常的**：

1. **品牌表本来就是主目录的子集** —— 例如 `Volkswagen` 表只登记大众相关的 OE 号，其他品牌相关的就不列。这是设计如此。
2. **同一产品确实对应多个 OE 号** —— 不同表登记了不同批次或不同市场的交叉号。

**所以程序做的是：把差异列出来，让人判断。** 全部标 `fitment_confidence = review_required`，**一个都没标 exact**。

### 4.2 为什么"286 个编号"这么多

因为只要一个 OE 号**没有出现在该编号涉及的所有工作表里**，就算一处差异。

举例：Bowen `3005` 出现在 6 张表里，它有 57 个 OE 号。
如果某个 OE 号只在 `Product Information` 和 `BYD` 出现，没在另外 4 张表出现 → 算 1 处差异。
`3005` 一个产品就贡献了 57 处差异。

**所以 1,843 行听起来多，但它是"覆盖范围差异"的完整清单，不是"1,843 个错误"。**

### 4.3 我加了一张"优先审核"表

1,843 行对人工来说太多了。所以 `oe-cross-sheet-review.xlsx` 有 4 个工作表：

| 工作表 | 行数 | 用途 |
|---|---|---|
| 填表说明 | — | 怎么填、每个下拉值的含义 |
| OE跨表差异 | 1,843 | 全量清单（备查） |
| **第一批优先审核** | **881** | ⭐ **先处理这张**，只含第一批候选产品的差异 |
| 按编号汇总 | 286 | 每个编号的差异统计，便于看哪个编号问题最大 |

**建议的处理顺序**：先看「第一批优先审核」，处理完再考虑全量表。

### 4.4 审核表要填什么

| 列 | 下拉可选值 |
|---|---|
| `Valid OE?` | `Yes` / `No` / `Unknown` |
| `Relationship` | `Main OE` / `Cross Reference` / `Vehicle-specific Reference` / `Incorrect` / `Unknown` |

`Relationship` 的含义：

- `Main OE` —— 主 OE 号
- `Cross Reference` —— 交叉参考号
- `Vehicle-specific Reference` —— 特定车型专用参考号
- `Incorrect` —— 错的

**这两列目前 100% 是空的。程序不判断。**

```

```

判断经验：

| 观测 | 可能是 |

| 共有 OE 多 + 规格相同 | 同一个产品（应合并） |

## 8. 如果只想先上线 50 个产品，最少需要人工确认多少条

### 8.1 直接答案

| 路线 | 产品行确认 | OE 关系确认 | 其他 | **合计确认记录** |
|---|---|---|---|---|
| **最省力路线（推荐）** | 50 | **279** | 3 | **332 条** |
| 全部 72 个都上线 | 72 | 881 | 16 | **969 条** |

我已用程序实际算过（脚本 `tools/calc-min-review.mjs`），不是估算。

### 8.2 怎么算出来的（最省力路线）

**第一步：50 行产品记录**

| 项目 | 数量 |
|---|---|
| 第一批候选总数 | 72 |
| 其中**数据完全干净**（无跨表 OE 差异 **且** 无错位问题） | **11 个** |
| 只有跨表 OE 差异、无错位问题 | 58 个 |
| 有错位问题 | 3 个 |

这 72 个的**数据本身都没问题**（只有 3 个有错位，且都是 MEDIUM/LOW，没有 HIGH）。
所以产品层面的门槛是：**先挑 50 个，确认它们的数据问题最少。**

**第二步：OE 关系确认（这是主要工作量）**

这是关键发现：**跨表 OE 差异才是真正的工作量所在。**

| 项目 | 数量 |
|---|---|
| 第一批候选中有跨表 OE 差异的编号 | **58 个** |
| 无跨表 OE 差异的编号 | 14 个 |
| 全部 72 个涉及的 OE 差异总行数 | **881 行** |
| **按"差异最少优先"挑出 50 个产品后，需要确认的 OE 行数** | **279 行** |
| 平均每个产品约 | 5.6 行 |

**为什么是 279 而不是更少**：因为无差异的只有 14 个产品，剩下 36 个必须从"有差异"里挑。
即使挑差异最少的，36 个产品平均也有约 7.7 行差异。279 = 36 个有差异产品的行数之和。

### 8.3 总工作量估算

| 项目 | 数量 | 每个字段约 30 秒 |
|---|---|---|
| 产品行 × 6 个字段 | 50 × 6 = 300 | 2.5 小时 |
| OE 行 × 2 个字段（Valid OE? + Relationship） | 279 × 2 = 558 | 4.7 小时 |
| 错位行 × 1 个字段 | 3 × 1 = 3 | 1.5 分钟 |
| **合计** | **861 个字段** | **约 7.2 小时（约 1 个工作日）** |

### 8.4 如果全部 72 个都要上线

| 项目 | 数量 | 估算工时 |
