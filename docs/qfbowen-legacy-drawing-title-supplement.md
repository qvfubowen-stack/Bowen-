## 二、发现 1：图纸文件名证据（价值最大）

### 2.1 Phase 3.5 当时为什么没能匹配

Phase 3.5 的匹配依据是**页面可见文本**（`tools/legacy/lib/match.mjs`）：
旧站规格表里的「博文编号」、OEM 号码、产品标题、页面 URL。

旧站 **813 个产品详情页里只有 552 个有规格表**（`legacy-products.json` → `with_spec_table: 552`）。
其余 261 页在页面上**没有写任何编号**，因此 Phase 3.5 把这批图片判为
`review_required`，理由原文是：

> 「旧站页面未提供任何可核对的编号（无规格表），不得自动绑定」

这个判断在**当时掌握的证据范围内是正确的**。

### 2.2 被漏掉的证据

旧站产品详情页正文里的图纸是带 `title` 属性的，取值就是**公司上传时的原始文件名**：

```html
<div class="p"><p><img src="/upload/image/20240402/17120219713778547.jpg"
                       title="4004.jpg" alt="4004.jpg"/></p></div>
                       ^^^^^^^^^^^^^^  ← 博文编号 4004
```

公司自己就是用产品编号命名图纸的。这条属性是**页面自带的结构化数据**，
不是从图片外观猜的，符合「不猜」的铁律。

### 2.3 结果（可复现）

对 Phase 3.5 已缓存的 943 个页面在**本地**重新解析（不联网）：

| 指标 | 数值 |
|---|---|
| 带 `title` 图纸的页面 | **262** |
| 解析出的编号在冻结产品库中命中 | **238** |
| 其中 `bowen_exact` / `bowen_variant` | 236 / 2 |
| **品类交叉校验冲突** | **0** |
| 编号不在产品库（见发现 3） | 24 |

**品类交叉校验**：每个候选编号在冻结产品库里的 `product_type`，与旧站中文品类换算后必须一致，
例如「节温器」↔ `Thermostat`、「热敏开关」↔ `ThermalSwitch`。
**238 条全部一致，0 冲突** —— 这是这条证据可靠性的主要支撑。

### 2.4 对人工工作量的影响

| 项目 | Phase 3.5 | 本补充之后 |
|---|---|---|
| `review_required` 图片 | **520** | 520 |
| 其中已预填候选编号 | 0 | **476** |
| 仍需从零排查 | 520 | **44** |

即：**从「520 张盲查」变成「476 张确认 + 44 张排查」**。

> ⚠️ **这不是自动绑定。** 文件名的证据强度低于「页面写明博文编号」，
> 因此随附工具输出的只是**候选值 + 校验结果**，最终仍需业务方在 XLSX 里确认
> （`status: candidate`，而非 `auto_match`）。

### 2.5 剩余 44 张没有候选图的是什么

| 类别 | 页数 | 张数 | 说明 |
|---|---|---|---|
| 图纸编号不在库（见发现 3） | 12 | **24** | 需业务方判断停产 / 漏登 |
| 产品页完全没有图纸 | 3 | **3** | 页 875「节温器」、978「马6芯」、1029「热敏开关」（无 `title` 属性） |
| **非产品图被混入产品图待办** | 11 | **17** | 证书页 1365/1366/1372/1373/1374/1375（6 页 × 2 = 12 张）+ 厂房页 1368/1369/1370/1371/1376（5 页 × 1 = 5 张） |
| **合计** | **26** | **44** | |

> 第三类值得注意：这 17 张其实**不是产品图**，Phase 3.5 已把它们按类别归到
> `images/certificates/` 与 `images/factory/`，却又同时出现在产品图的
> `review_required` 列表里。**建议直接从产品图待办中剔除**，
> 真实需要排查的量可降到 **27 张**（12 页缺编号 + 3 页无图纸）。
>
> 另注：6 个新闻页（557–562）虽然也有 `title`（`01.jpg`–`06.jpg`），
> 但它们**没有进入** `review_required` 列表，不属于这 44 张。

## 五、必须澄清的两点（避免误判）

### 5.1 「产品图没接入网站」不是缺陷，是业务方要求的冻结

本次调查中一度把「英文站产品页仍显示 `Photo pending`」当作问题，
**这个判断是错的**。项目文档已在多处明确记录这是**有意为之**：

- `delivery/04_known-issues.md` 2.1：「**按业务方要求暂未接入网站**」
- `delivery/02_ui-prototype-report.md`：「按业务方要求，本阶段暂未把图片接入网站」
- `docs/excel-image-audit.md`：图片已提取并映射（681 文件 / 798 对象 / 403 个产品主图）

因此**不需要**「修复」它；需要的是业务方解除冻结。本次调查**未改动任何网站文件**。

### 5.2 本次下载的素材已全部删除（312/313 与 Phase 3.5 重复）

调查初期我独立抓取了 350 张图片，随后发现 Phase 3.5 已下载 **870 张**
（`data/legacy-site/images/`）。逐文件 SHA-256 比对结果：

| 项目 | 数量 |
|---|---|
| 我下载的唯一文件 | 313 |
| **已存在于 Phase 3.5** | **312** |
| 我独有的 | 1（实际为 4 个 1.2 KB 的 QQ 图标，无价值） |

因此**我的素材副本已全部删除**（节省 64.9 MB），避免与 Phase 3.5 的归档形成两套真相。
被删除/未采纳的内容见第六节。
