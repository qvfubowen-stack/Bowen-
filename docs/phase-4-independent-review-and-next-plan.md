# Phase 4 独立审阅与下一阶段方案

审阅日期：2026-09-26。

## 结论

Phase 4 的真实素材与公司资料接入基本完成，可以保留现有实现继续推进。独立运行构建、数据检查、RFQ 浏览器测试，并检查了实际页面；交付报告中的主要数量与测试结果能够复现。但“全部验收通过”只代表现有测试覆盖的范围，不能等同于已经适合对外上线。

建议先执行 Phase 4.1：公开展示规则与英文页面收尾，再进入真实询盘服务，最后准备 SEO 与部署。无需重新抓旧站，也无需让业务人员现在处理待确认图片。

本次为审阅与方案交付，没有修改网站业务代码、源数据或发布状态。会触发数据重建的数据库验证以及生产构建均在临时副本中执行。

## 一、用户本轮确认的口径

1. IATF 证书上的街道地址可以对外使用，不再作为待决策项。
2. 无可靠图片的产品暂不进入网站产品库，不显示占位产品卡片或详情页。
3. 没有证书图片的认证暂不展示，包括首页、About、Quality、元描述等入口。
4. 产能和标准交期继续不做；人工确认记录继续由后续业务人员跟进。

实施时保留原始资料和内部待完善记录；“不进入网站产品库”应由网站数据导出与查询统一控制，不需要删除原始 Excel 或历史证据。

## 三、需要处理的发现

### 1. [P1] 发动机代码提取会截断原文，且把车型代号当发动机展示

位置：`website/src/lib/engine-code.ts:30`、`website/src/lib/repositories/json-repository.ts:303`。

直接运行当前提取函数得到：

| 原始文本 | 当前结果 | 问题 |
| --- | --- | --- |
| 4G6 | 空数组 | 漏掉数字开头的发动机代号 |
| 4G13/4G15S | G13、G15S | 删除了首位数字，改变了代号 |
| 476ZQA | 空数组 | 漏掉数字开头的代号 |
| A4L F150 X1X3X5X4X6 | 全部作为候选代码输出 | 车型/混合字符串被当作发动机标签 |
| EA888 | EA888 | 此例正常 |

实际 BW-3005 页面已显示 G13、G15S 等截断结果；首页出现 A4L、F150、X1X3X5X4X6 等发动机筛选标签。属于既有功能问题，本轮并非认定它由 Phase 4 新引入，但会影响客户识别产品。

建议：立即停止展示不可靠的独立发动机标签；保留原始适配行及 OE 关联。提取逻辑必须保留完整字符串，不可仅扩大正则后就将所有字母数字串宣称为发动机。后续使用有依据的 engine/model 区分；暂不能确认的内容只放在一般应用信息里。

### 3. [本轮新规则] ISO 14001 / ISO 45001 仍以文字形式对外展示

当前两项认证确实没有图片，但仍出现在 Quality 卡片、首页、About、元描述和相关文字中。应从公开展示集合隐藏，保留内部来源记录。

有图管理体系认证目前保留 IATF；其余 3 张有图材料作为荣誉/公示展示。创新型中小企业材料是公示名单，继续标成 public list，不应改叫体系认证证书。

同时移除“three management systems”“Three certificates”以及解释为什么没有 ISO 图片的内部说明。更新 `website/tools/verify-prototype-data.mjs:281` 中强制恰好三个认证的旧断言，以及 p4-live-check 中必须出现 ISO 字段的旧预期。

### 4. [P2] 公开页面仍有大量内部原型和数据处理说明

位置：`website/src/components/ProductCard.tsx:29`、`website/src/app/(site)/products/[id]/page.tsx:92`、`website/src/components/SiteFooter.tsx:75`、`website/src/app/(site)/contact/page.tsx:50`。

实际页面可见：

- Prototype # / Prototype candidate #。
- Subtype: not used in V1。
- Source sheets、中文工作表名、审核表行号及分类过程。
- Contact 解释“不展示地址是因为资料没有地址”。
- Quality 大段说明“证书缺图”“来源页码”“如何证明资料可靠”。
- Blog 仍为占位页，但主导航和页脚都有入口。

这些有助于内部验收，但不宜占据客户页面。证据追溯留在数据和报告中；公开页面展示产品、适配、规格、公司与询盘信息。英文页面中的品牌名应使用明确的中英别名表合并展示，不应将中英文写法算成不同品牌。

原始应用内容要保留；对无法可靠整理的中文适配内容，可暂不展示独立的车型/发动机字段，不要未经复核整段机器翻译上线。隐藏空 Blog 入口即可，不需要为了填满导航临时生成文章。

### 5. [P2] “无编造内容”结论超过了现有证据与测试覆盖

位置：`website/src/app/(site)/quality/page.tsx:30`、`website/src/app/(site)/page.tsx:373`。

页面断言存在六个质量检查环节，并称测试结果与生产批次绑定、可追溯，首页还提到校准量具。已检查的宣传手册文本能支持调整测试设备和寿命试验台，但没有找到上述具体流程承诺的对应依据。

这不等于认定公司没有这些流程；只是当前报告不能证明它们。现有 p4-live-check 通过扫描少量营销关键词，无法证明所有能力描述都有来源。

建议保留有图片和手册支撑的设备、认证范围；缺乏明确来源的流程承诺先移除或收敛。后续业务提供质量文件时再补，不必现在新增人工确认任务。

### 6. [P2] 校验脚本仍带构建副作用，图片验证也未完整检查源映射

位置：`tools/verify-product-db-v2.mjs:15`、`tools/build-product-db-v2.mjs:1039`、`tools/p4-build-site-assets.mjs:366`。

- verify-product-db-v2 仍 import 顶层会写文件的 build-product-db-v2。本次临时副本运行也证实，“验证”会先重建数据。把公司资料搬到配置文件解决了被覆盖丢失的问题，但没有消除这个副作用。
- p4-build-site-assets 的 verify 中，名为 reviewLeak 的检查实际只判断 product_id 是否存在于网站产品表；它没有重查源映射是否 exact/primary，也没有对产品图做源文件哈希一致性检查。
- 本次另做独立比对，当前 394 张确实全部正确；这里是后续回归保护不足，并非已经发现错绑。

建议将 oeSearchKey 等纯函数移到公共模块，构建使用显式 main 入口；验证命令保持只读。产品图校验应检查映射状态、主图唯一性、文件存在和字节/哈希一致性。建立统一的数据与资产生成命令，避免后续刷新数据后图片映射未同步。

## 四、下一阶段执行方案

### Phase 4.1：公开展示规则与英文内容收尾（优先）

1. 将已经确认的地址写入公司资料配置，并用于 Contact 和必要的页脚信息：

   `No. 3, Duzhi Road, Qufu Electronic Information Industrial Park, Jining City, Shandong Province, 273100, China`

   本次已打开 IATF 原图核对该文字；用户已确认可用，不再重复询问地址。移除地址缺失的旧说明，不据此新增营业时间、地图坐标或其他信息。

2. 建立有可靠图片才进入网站数据的准入规则。保留原始资料，公开目录仅导出符合状态与图片条件的产品，并同步导出其 application/OE 索引。避免以已过滤的网站产品表反向决定图片资格而产生循环依赖，应从内部产品状态和源图片映射共同计算发布集合。

3. 建立有图证书的公开展示集合，并同步所有页面和元描述。IATF 与荣誉/公示分开呈现。

4. 修复完整发动机代号保留问题，先隐藏无法证明为 engine 的候选标签。两处不同的提取逻辑统一处理，保持原始 application 与 OE 关系。

5. 清除客户页面的原型标记、内部分类解释、原始工作表名和地址/证书缺失说明；处理明确的英文品牌别名，隐藏空 Blog 入口。

6. 收敛无明确来源的质量流程承诺；保留已证实的设备与认证事实。

7. 修复验证副作用，增强资产来源检查，串联数据/资产刷新命令。更新报告和测试，不再把全部测试通过描述成“全部事实已经证实”。

验收应包括：22 个无图产品不出现在列表、搜索、直接详情和 RFQ 可选项；首页和分类数量由同一发布集合计算；没有两项无图 ISO 的公开宣传；地址正确；原型说明从客户页面消失；`4G13` 不得变为 `G13`；所有正式图片仍可加载；数据、类型、构建和 RFQ 回归通过。noindex 继续保留。

### Phase 5：真实询盘闭环

Phase 4.1 验收后，再实施服务端 RFQ 接收、输入校验、错误重试、防重复/限流、询盘持久化和邮件通知。用当前邮箱作为收件地址候选，不代表已经具备发信服务凭据。

邮件凭据通过环境变量配置；真实附件若开放，落实类型和大小限制及存储。收到服务器确认后才显示提交成功，网络失败保留用户填写内容。询盘保存原有 product_id/application_id/OE/数量关系。

发信服务、正式发送域名和凭据在该阶段确定，不需要在 Phase 4.1 之前阻塞收尾。数据库可以继续使用当前静态 JSON 作为产品来源，暂不为接询盘而全面迁移 Supabase。

### Phase 6：SEO 与部署准备

确定正式域名和托管方式后，完成英文路由策略（结合此前 /en/、/zh/、/es/ 规划）、canonical、sitemap、结构化数据、必要的隐私说明、图片体积与移动端性能检查。只为实际发布的有图产品生成 SEO 数据。

先部署到预览环境并保持 noindex；完成真实询盘与页面验收后，再切换正式索引策略。不能仅删除界面上的 Prototype 文案就认为网站已正式上线。

## 五、对原交付的评价

可以保留：真实图片接入、集中媒体访问层、公司资料配置、原始数据保护、IATF 范围披露、测试和构建基础。

需要修正：公开展示口径、发动机标签、英文客户页面文案、质量能力的证据边界、校验脚本副作用。

下一步不需要推倒重做，也不需要重新处理几百条待确认素材；围绕现有 394 个有图产品完成一次明确的展示规则与内容收尾即可。
